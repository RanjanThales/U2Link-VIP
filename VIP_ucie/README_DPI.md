# UCIe SystemC <-> SystemVerilog DPI Testbench v2

This package is a corrected version of the first DPI bridge.

## What changed in v2

1. Removed the old SystemC `timeout_guard()`.
   - Test ownership has moved to SystemVerilog.
   - SV now controls test sequencing and final timeout.
   - SystemC no longer calls `sc_stop()` in the middle of an SV test.

2. Removed the old SystemC test-sequence `run()`.
   - SystemC now owns infrastructure only:
     DUT, Connections channels, RX monitor, and loopback.

3. Added a SystemC DPI command mailbox.
   - DPI C functions are non-timed.
   - They enqueue commands.
   - `UcieDriver::command_service()` performs `Push()`, `wait()`, and read-response synchronization.

4. Added `ucie_dpi.h`.
   - C/C++ declarations are centralized.

5. Added `ucie_dpi_pkg.sv`.
   - DPI imports.
   - Blocking SV tasks:
       ucie_write()
       ucie_read()
       ucie_send_word()
       ucie_send_frame()
   - Every transaction has a timeout.
   - SV does not call SystemC `wait()`.

6. Added `sv_top_dpi.sv`.
   - TEST1..TEST6 are SV tasks.
   - The original test order and register accesses are retained.

7. Reset is still generated by SystemC.
   - This preserves the supplied SystemC top behavior:
       assert at 2 ns
       deassert at 12 ns

## Important

The supplied UCIe model currently spends about 4 ms in its link state machine before reaching ACTIVE. Do not replace that with a short ns-scale wait.

## File integration

Use:

    sc_top_dpi.cpp
    ucie_dpi.h
    ucie_dpi_pkg.sv
    sv_top_dpi.sv

along with your existing:

    ucie_top.h
    ucie_top.cpp / related model sources
    nvhls_connections
    nvhls_int
    madsim sources
    other project headers/sources

Do NOT compile the old `sc_top.cpp` at the same time as `sc_top_dpi.cpp`.

## Questa / MTI_SYSTEMC

The SystemC source retains:

    SC_MODULE_EXPORT(tb_export);

when compiled with `MTI_SYSTEMC`.

The SV side instantiates:

    tb_export u_sc_top();

The C DPI functions are linked into the same SystemC shared library.

A typical flow is conceptually:

    vlog -sv ucie_dpi_pkg.sv
    vlog -sv sv_top_dpi.sv

    vlog ... / compile SystemC library containing sc_top_dpi.cpp ...

    vsim SV_TOP
    run -all

Your exact `sccom`/`scgenmod`/`vlog` command line depends on the existing Questa SystemC build setup and include/library paths.

## Expected first debug milestone

The first milestone is:

    @2 ns Assert reset
    @12 ns Deassert reset

followed by the UCIe LTSM reaching:

    LINKINIT -> ACTIVE
    PHY: RESET -> ACTIVE

Then SV should successfully execute:

    ucie_read(REG_AFE_LINK_DONE, link_done)

and print:

    TEST1 PASS: AFE_LINK_DONE=1

If it instead hangs inside a DPI call, the SV timeout should now report:

    UCIe DPI transaction timeout

rather than the previous SystemC:

    TIMEOUT GUARD stopping simulation

That distinction is intentional and makes the next debug step much easier.

## Note on RX/read-response discrimination

The current supplied SystemC protocol has a shared RVA response stream. The existing design identifies a register response using `read_pending`, as in the original driver. v2 preserves that behavior so it does not silently change the supplied model's protocol semantics.

For a production VIP, the next refinement should be a transaction tag/type in the response path if the protocol/model exposes one. That would eliminate any ambiguity between register-read responses and streaming RX words.
